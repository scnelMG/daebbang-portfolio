# 아키텍처와 추천 설계

## 서비스 요청과 배치 작업

온라인 경로는 React → Spring API → MySQL입니다. 사용자가 빵과 태그를 고르면 API가 저장된 점수 테이블을 읽어 결과를 구성합니다. 리뷰 수집·LLM 호출·Spark 집계는 추천 요청 안에서 실행하지 않습니다.

오프라인 경로는 Python 수집·정제 → MongoDB 원문 → LLM 태그 분류 → MySQL 라벨 → Spark 집계입니다. 회원 리뷰 태그도 Spark 입력에 합쳐집니다. 단일 배치가 모든 실행을 원자적으로 보장하는 구조는 아니며, 데이터 최신성은 단계별 실행 완료와 주기에 영향을 받습니다.

## LLM과 계산의 역할 분리

`LabelingService`는 분류 결과를 태그 사전에 대조하고 중복 태그와 충돌하는 유형 태그를 처리합니다. LLM은 리뷰가 언급한 태그를 선택하고, 추천 점수는 `ScoreAggregationJob`에서 계산합니다. 사전에 없는 응답을 버리는 검증이 분류 정확도를 보장하는 것은 아닙니다.

## 집계 공식

```text
w = 0.5 ^ (경과일 / 180)
score = (태그 언급 리뷰의 가중합 + m × μ) / (전체 리뷰의 가중합 + m)
α = 회원 리뷰 표본 수 / (회원 리뷰 표본 수 + 10)
final = α × 내부 점수 + (1 − α) × 외부 점수
```

- `μ`: 빵·태그 조합별 빵집 평균 비율. 언급이 없는 빵집도 분모가 있으면 0 비율로 포함합니다.
- 외부 리뷰 `m=5`, 내부 리뷰 `m=3`, 반감기 180일을 사용합니다.
- 집계 결과는 한 MySQL 트랜잭션 안에서 기존 행을 지우고 새 결과를 삽입합니다.
- 분류는 신규 문서를 중심으로 처리하고 점수는 전체 재계산합니다.
- 공식이 결정적이라는 것은 같은 입력과 같은 기준일에서 결과를 설명할 수 있다는 뜻입니다. 원문·시각별 입력과 가중합이 보존되지 않으면 저장된 정수 건수만으로 과거 점수를 완전히 재현할 수는 없습니다.

## 후보 선택

1. 요청의 빵·태그 조합을 검증합니다.
2. 빵집별로 데이터가 있는 선택 태그의 점수를 평균합니다.
3. 선택한 빵 n종 중 최소 ⌈n/2⌉종에 근거가 있는 빵집을 후보로 둡니다.
4. 데이터가 있는 빵 점수의 평균으로 영업 중 상위 최대 2곳을 고릅니다.
5. 영업 중 미선정 빵집에서 탐색 슬롯을 무작위로 채웁니다.

근거가 없는 선택 태그는 현재 구현의 평균에서 제외됩니다. 태그 두 개를 선택했다고 두 특징이 모두 입증되는 논리적 AND 조건은 아닙니다. 탐색 결과는 실제 빵 판매 여부를 확인한 추천도 아니므로 별도 표시와 방문 전 확인 안내를 유지합니다.

## 분산 구성의 범위

팀 자료에서는 MongoDB 3노드 레플리카 구성이 로컬 시연용으로 존재하며, 운영 이전 과정에서는 단일 멤버가 관측됐다고 기록합니다. Spark master·worker를 같은 서비스 서버에 배치한 기록도 있습니다. 이를 다중 물리 노드 성능 검증이나 운영 고가용성 보장으로 표현하지 않습니다.

이번 공개본에서는 인프라를 실행하지 않았으며, 배포 설정·운영 주소·자격 증명은 제외했습니다.
